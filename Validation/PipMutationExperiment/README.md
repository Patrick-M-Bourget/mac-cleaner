# Genuine pip mutation-boundary experiment

October23,2026 · #24/#25 · **The vendor command is unsuitable for the app's exact frozen target manifest; production mutation remains disabled.**

This extends the genuine read-only21.2.4 inventory evidence rather than repeating it. It invokes the actual pip vendor removal command in a newly owned virtual environment/cache. Wheel-shaped ZIP fixtures and HTTP sentinels are seeded by the harness; they are not downloaded, generated by a pip build, installed or executed. The experiment establishes command targeting behavior, not genuine historical cache provenance or arbitrary Python safety.

## Reproduce

```sh
/usr/bin/python3 -I -B Validation/PipMutationExperiment/run.py > /tmp/still-pip-mutation.json
```

Requires the existing trusted Apple Command Line Tools Python with bundled ensurepip21.2.4 (observed Python3.9.6, macOS27.0.1/arm64). The script accepts no external root/interpreter/cache and creates one private0700 `StillPipMutation-*` temporary tree. It uses `venv.EnvBuilder(with_pip=False)` followed by that venv's bundled ensurepip. No global install, dependency download or personal interpreter/cache discovery occurs. HOME, TMPDIR and five independent caches are owned; environment uses fixed PATH, PIP_CONFIG_FILE=/dev/null, PIP_NO_INDEX=1, version-check suppression and Python-I/-B. Commands use argument arrays, null stdin and bounded subprocess timeouts (45s provisioning,15s each command). No network operation is requested; packet-level network absence is not independently traced.

For each case, actual `cache list --format=abspath` observes the initial cache. The reviewed manifest contains one wheel path and device/inode identity. The harness then creates two post-review matches (same filename in another cache subdirectory and a second package version), or replaces the original entry's inode. Each scenario uses its own cache; mutation cannot leak into another scenario or real user cache.

## Actual public-command observations

All commands share this prefix:

```text
<owned-venv>/bin/python3 -I -B -m pip --disable-pip-version-check
  --cache-dir <owned-cache> cache remove <argument>
```

[Observed machine-readable report](evidence.json):

| Remove argument | Actual result | Exact-manifest consequence |
|---|---|---|
| Absolute reviewed wheel path | Exit1, `No matching packages`;0 removed | Cannot use a full path as an exact target in this version |
| Full wheel basename | Exit1, `No matching packages`;0 removed | Literal filename is not an exact-file removal interface here |
| `still_fixture-1.0-` | Exit0,2removed | Reviewed wheel **and post-review same-name wheel** removed; new version retained |
| `still_fixture` | Exit0,3removed | Reviewed wheel plus both unapproved new entries removed |
| `still_fixture-1.0-`, after inode replacement | Exit0,1removed | Replacement at the reviewed path removed; vendor command does not bind reviewed resource identity |

In every case the other-package wheel and HTTP sentinel remained byte-identical. All1,268 snapshot entries under protected project/venv/HOME retained names, file hashes/sizes, modes, modification times and symlink destinations. Access times are excluded because verification itself reads owned files. The tree was removed afterward. No real user data, permissions, services, notifications or browser state were touched. No app feature or positive adapter allowlist changed.

## Decision and limits

Refuse `pip cache remove` as an executor for the current exact path/resource approval contract. It freshly enumerates pattern matches, widens to post-review entries and does not validate resource identity. Changing a confirmation to show a broad pattern would not silently satisfy the accepted exact-target/new-discovery contract. `cache purge` is not a workaround: it is a broad operation and was not run here. No automatic retry or Trash recovery is implied.

The observed full-filename behavior is specific to21.2.4: its published implementation appends wheel glob suffixes based on the supplied pattern. That implementation detail explains the result; it is not a stable API to normalize around or a claim about current26.x behavior. Real pip execution is distinct from the deliberately seeded data.

This useful negative result does not complete all #25 acceptance: concurrent owners, actual denied-access/timeout/cancellation/partial outcomes and durable application journaling remain unqualified. Existing Process-boundary tests cover limits synthetically; they are not relabelled as pip mutation qualification. Arbitrary interpreter startup/module provenance, other versions and HTTP-v2 layout also remain unqualified.

A future exact-leaf alternative would need independently validated cache provenance/version/layout, ownership coordination, descriptor-relative identity revalidation and durable intent/outcomes before product integration. This experiment does not implement or authorize that alternative. Retain read-only inventory and guidance now; #25 remains conditional rather than adding an action that cannot honor the reviewed manifest. Independent #30/#32 work can proceed without broadening this experiment.
