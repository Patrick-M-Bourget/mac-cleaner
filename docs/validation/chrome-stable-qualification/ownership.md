# Chrome #18 ownership and final-unlink decision — October 25, 2026

Decision: stop before another broad native experiment. No supported external exclusive ownership/coordination guarantee has been established. This is a bounded evidence-based qualification blocker, not a claim that all possible designs are impossible. Keep #18 open and #19 blocked; positive production allowlist remains empty. No production code, tests or workflow changed. No personal browser was inspected/launched/downloaded. No new Stable experiment was dispatched.

- [Backend cleanup tracker header](https://chromium.googlesource.com/chromium/src/+/d586be9fa9b8009487056edccf01555bb18dc3b2/net/disk_cache/backend_cleanup_tracker.h) describes an internal refcounted backend-work sequencer. [Implementation](https://chromium.googlesource.com/chromium/src/+/d586be9fa9b8009487056edccf01555bb18dc3b2/net/disk_cache/backend_cleanup_tracker.cc) stores the registry in a process-local static map protected by a thread lock. It supplies no third-party process lease.
- [Apple flock manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html) specifies advisory coordination among cooperating processes. Merely locking a directory/cache file does not prevent an uncooperating browser or same-user writer from changing names/data. Its old-singleton migration use cannot establish a current, documented external cleaning protocol.
- [Apple unlink manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/unlink.2.html) describes removing the named directory entry. It can remove a name while another process still holds the underlying object open; no browser-owner exclusion follows from successful removal.

## Exact residual race in current disposable helper

`Validation/ChromeProbe/remove-owned-cache.py` opens canonical bounded directories using no-follow descriptors and checks each approved regular leaf identity, size, mtime and link count. It repeats identity/size/mtime with `os.stat(name, dir_fd=parent_fd, follow_symlinks=False)`, then separately calls `os.unlink(name, dir_fd=parent_fd)`.

A writer can replace that directory entry after final stat and before unlink. The name can then reference a different object from the approved manifest; unlink removes that changed entry. Directory-relative access prevents ancestor/path escape but does not make the stat/unlink pair an atomic compare-and-remove. The target can also be modified in place after final stat. A process observation before the pair cannot exclude Chrome reopening or a helper writing within that interval. A symlink replacement is not followed by unlink, but it would still remove an unapproved replacement entry. Opening the approved file descriptor alone does not turn name-based unlink into identity-conditional deletion.

Existing public helper tests already prove refusal for substitutions present before validation. Adding another such fixture would not prove this final interval safe. A timing stress or monkeypatch of private calls would neither establish production exclusion nor fix the contract, so none was added. Existing qualification truth already says this helper is experimental and cannot qualify installed Chrome.

## What would resolve the blocker

Evidence of a vendor-supported cache-maintenance API, externally enforceable lease/cooperative protocol honored throughout cache operations and browser reopen, or a separately approved design with genuinely enforceable isolation and exact-target semantics could justify a new bounded qualification proposal. It must include helper/network processes, configured roots/policy and reviewed-target changes. Private singleton impersonation, advisory file locks, transient process lists and descriptor preflight alone are insufficient.

If such an approach is established, the next experiment must then use one genuinely verified Google Chrome Stable build on an ephemeral hosted machine, record official binary/version/signature/OS/root provenance, and qualify real protected semantic fixtures plus active/reopened/changed/denied layouts. Downloading Stable merely to repeat the successful closed-owned-process CfT test cannot establish the currently missing coordination guarantee. Therefore do not spend another broad run on it now.
