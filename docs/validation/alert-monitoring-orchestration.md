# Alert monitoring orchestration

The production monitoring controller now lives in the StorageAlerts package. The native app supplies only OS operations through `AlertMonitoringSystem`: notification authorization/submission, startup capacity, time, persisted episode state and the 15-minute tolerant timer. `StorageAlertsController` retains native notification actions and delegate presentation. Views, labels, threshold semantics and future-milestone gating are unchanged.

This implements the existing M5 contracts in SPEC.md and the Storage alerts handoff: re-enabling must resume authorized capacity monitoring, unavailable effective monitoring must not leave an alert-only poller, and explicit Quit stops monitoring while preserving preference/login intent.

## Reproduced failures and fixes

Public `AlertMonitoringController` actions and observable monitoring state are exercised with controlled system operations; the tests never request real notifications, alter login registration or scan files.

- Start monitoring, hold an activation's authorization response, disable and re-enable. Previously the old process-wide sampling flag discarded the new sample; requested alerts remained on without effective monitoring or a timer until another activation. Sampling now belongs to its monitoring generation. The new generation starts exactly one poller; late denied authorization from the old generation cannot stop it. Capacity is sampled for the renewed enable, and the same low episode remains suppressed without another notification.
- A newly observed startup capacity smaller than the configured threshold previously marked monitoring ineffective but retained its poller. The invalid-threshold path now cancels polling while retaining the saved preference and existing actionable status.
- Stopping for termination during held authorization previously allowed its completion to restart polling. Termination now invalidates the monitoring generation before cancellation. It preserves the saved enabled preference and independent login intent.

Each regression was observed failing against the extracted existing behavior before its fix. Tests assert public effective state, actual controlled pollers/capacity observations and notification outcomes, rather than private generation flags. Existing durable episode, reservation and delivery-gate tests remain intact.

## Verification and limits

At source `b0546d2`, all 31 StorageAlerts package tests passed on the local and hosted arm64 development environments. The native Debug app compiles with the same production controller source. This is focused feature verification, not a full native suite or real notification/service-management qualification. No visible presentation changed, so no new visual acceptance is claimed. Real authorization UI, native notifications, window-close/menu-bar interactions and login approval still require disposable OS qualification; commercialization signing remains separate M8 work.

Independent review reproduced a fourth issue newly reachable through renewed sampling: an old held submission completed after disable/re-enable, genuine recovery and acceptance of a fresh low episode. Fixed-identifier stale cleanup erased the fresh pending request while its episode remained suppressed. The public regression first failed with an empty pending-request model. Every submission now receives an immutable identifier; stale completion removes only its own identifier. Opt-out/reset cancel captured in-flight and last-accepted identifiers, including the previous-version fixed `Still.lowSpace` identifier. The fresh episode's notification survives the obsolete completion and is not replayed at the next check. Cancellation ownership is stored with episode intent before submission and recovered across controller/process restarts. The optional Codable field accepts old records without discarding their suppression. Public restart tests round-trip saved policy JSON against retained controlled OS pending state, then verify both opt-out and Reset remove the prior-process request. A recorded pre-ownership JSON fixture verifies the accepted low episode remains suppressed. Tracking retains in-flight attempts plus the last accepted request, pruning exact retired IDs after acceptance; no asynchronous broad enumeration or global prefix removal is used.

A separate pre-existing lifecycle gap was then reproduced: after an accepted Quit stopped monitoring, a later activation/configuration while the process waited for an operation boundary restarted its poller. `stopForTermination` is now terminal for that controller/session. Activation, queued configuration and preference actions cannot resume monitoring; a new process/controller restores the saved preference. Ordinary disable and Reset use a resumable pause instead, preserving their existing re-enable journeys. The public regression failed before the terminal latch and passes after it.

The threshold editor is distinct from the applied preference. A public regression reproduced another pre-existing issue: clearing the field while monitoring, before choosing Apply, caused the next activation sample to stop effective monitoring and cancel its poller. Sampling now validates the applied policy threshold; editor validity still governs Apply and explicit opt-in. The regression verifies invalid and valid-but-unapplied edits retain monitoring and the saved 40 GB setting; Apply alone saves the new setting, without bypassing the existing low-episode suppression. Sampling cadence remains unchanged.

A final public regression reproduced unfinished notification work surviving explicit Quit: a held submission completed after monitoring stopped and left an accepted pending request. Graceful termination now invalidates delivery ownership and cancels exact known request identities, while preserving enabled intent and uncertain/accepted episode suppression. Its late completion can remove only its own immutable ID. The restart cancellation test separately simulates abrupt process exit (not graceful Quit), so it continues proving recovery of durable ownership rather than relying on graceful cancellation. No delivered-banner recall is claimed.

System acceptance is still distinct from display. Pending-request cancellation does not recall already delivered banners; genuine OS delivery remains a disposable qualification task.

## Global Reset when future alerts are hidden

A normal launch omits the future-milestone flag, so initialization deliberately does not restore alert preferences or enable monitoring. The public Reset journey nevertheless remains available. A regression reproduced that this launch forgot the preceding process’s UUID request identities and deleted their saved record while leaving those requests pending. Explicit Reset now reads saved cancellation ownership before deleting state and unions it with current/in-flight ownership. Only those exact identities and the legacy fixed identifier are canceled; unrelated requests remain untouched. This read does not enable the hidden feature, authorize notifications or start polling.

The public controlled-system regression creates a genuine prior-controller request, restarts with feature availability off, and verifies Reset removes the owned request and preferences while preserving an unrelated request. A second regression, also observed failing against the prior production behavior, verifies unreadable ownership causes Reset to throw without deleting the saved authority or pending request; after the read becomes available, retry cancels the request and completes. Both pass in the focused 31-test StorageAlerts package suite. No real notification/login state, OS permissions or personal files were accessed. The native interface and presentation are unchanged; this addendum adds no real OS qualification or new visual acceptance claim.
