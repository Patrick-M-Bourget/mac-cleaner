# CacheDrop: behavior spec

This spec covers behavior the prototype can't show. The screens, layout and copy come from the prototype (`docs/visual/preview.html`, full mode). Where this spec and an older doc disagree, the **Decisions** in [RESET.md](RESET.md) win, then this spec. The PRD, research and field note are background.

## 1. Product principles

- CacheDrop answers four questions: what takes space, what can be removed, what happens if it is, and how much space came back.
- Size, age and location only suggest candidates. Every candidate is judged on three questions: who owns it, how it comes back, and whether anything uses it now.
- One selection is shared by Smart clean, the Cleanup plan and Applications (#349, Decision 67): recommended items start ticked everywhere and the user unticks or adds from any page. The user picks categories or items in the plan, or opens Smart clean, the recommended plan on its own page (a safe plan that passes the checks: caches, build data, updater downloads, logs, leaked app copies, caches a tool cleans with its own command, Downloads files not opened or changed in 7 days (#342) and files from deleted apps that a bundle ID or receipt ties to the app (#319), never an item the user chooses one by one, such as an older JetBrains version's folder, which holds local history, or an old temporary file (#144); all ticked, each can be unticked). Either way the user reviews the consequences before anything changes. An untick on one page shows on every page that lists the item and survives rescans; a newly found recommended item arrives ticked.
- Every item is checked again just before CacheDrop acts on it (section 4).
- Scanning never writes. Choosing scan locations never means consent to clean.
- Unknown is shown as unknown, never as 0. A location CacheDrop can't read is listed as not accessible, not left out of the picture.
- Estimated space, space moved to Trash and measured freed space are three separate numbers, always labeled (section 6).
- No account, telemetry or AI service. All scanning and cleanup happen on the Mac; only a requested update check contacts the update feed (Decision 102).
- No automatic cleanup. CacheDrop only acts when the user confirms a reviewed plan.
- Catalog and Explore storage expose lifecycle completion only after discovery and final History and Storage trends writes finish, including when stopped (Decision 98). Optional later cleanup measurements have separate completion: a lifecycle handoff skips sleeping checks and awaits running measurements and saved findings; ordinary cleanup and quit policy stay unchanged (Decision 99).

## 2. Safety rules

These hold for every category, in every milestone.

- **User files go to Trash.** CacheDrop never empties the Trash. It deletes from the Trash only items it moved there itself, and only when you ask (RESET Decision 68). Finder's Empty Trash is never scripted, and the user's own trashed files are never touched.
- **Never touched:** browser logins, cookies, history, passwords, autofill, site data (IndexedDB, Local Storage, service-worker data), sessions and profile settings; the Photos, Mail and Messages databases; app binaries and signed bundles (except Chrome's leaked code-sign copies, section 3, and an app or plug-in the user chose to uninstall, which goes to the Trash, RESET Decisions 41 and 50); other users' data; system files.
- **Protected rules in the catalog.** Codex's protected-data lists become catalog rules that no cleanup rule can override: Chrome logins, cookies, history and profiles; Xcode Archives and anything outside DerivedData (project source). Everything inside DerivedData, built products and dSYMs included, is regenerable build output.
- **A cache folder can hold live work.** A git working tree inside a cache folder is never a candidate. One exception (#160): SwiftPM's own dependency clones, a `.git` folder at exactly `.build/checkouts/<name>/.git` in a `.build` beside its `Package.swift`, are build output it fetches again, so they don't keep that `.build`; any other git working tree in it, a nested one included, still does, at the scan and at the check. Known load-bearing caches (such as ccache) and CacheDrop's own tools are never offered, nor CacheDrop's own folders or those of Still, its former name (#149).
- **Owning app must be closed.** If the app that owns a candidate is running, that candidate is refused with a reason. For files from a deleted app, the owner is the app's maker: any process of that maker counts as running, for any user, background helpers and daemons included, not only an open app (#240). When the process list can't be read, the file is held back with "Couldn’t check whether … is running", never treated as closed. CacheDrop never force-quits, and quits apps only when you ask: the plan's **Quit <App>** link sends a normal quit request, like ⌘Q, which the app may answer by asking to save or by refusing. CacheDrop never asks for Accessibility to quit an app. When the app quits, CacheDrop checks again; when it doesn't, the plan says it is still open. A command-line tool isn't an app: the plan says "Quit <tool> to include this" with **Check again**.
- **No admin rights.** CacheDrop never asks for an administrator password and never installs a helper. An item it can't change as the user is skipped and reported.
- **Exclusions win.** An item inside a user exclusion is never a candidate.
- **No transactional rollback.** Items are handled one at a time. CacheDrop never claims a multi-item undo.
- **Tests touch only temp fixture folders**, never real user paths.

## 3. Kinds of data and their action

Each category is a rule in a data catalog: paths, owning app, kind of data, action, protected patterns and the consequence text shown at review. There is no version gating: a rule applies whenever its paths exist, and its protected patterns and per-item checks keep it safe.

Decision 3 sets the main split: regenerable data is deleted permanently; user files, models, VM images and installers go to Trash.

| Kind | Examples | Action | How it comes back |
|---|---|---|---|
| Cache | npm, Yarn, pnpm metadata, pip, Cargo, Gradle, CocoaPods, Homebrew cache; browser cache folders; per-app `~/Library/Caches`; caches apps keep elsewhere (#133): VS Code, VSCodium, Cursor and Windsurf cache folders, older JetBrains IDE versions' caches, Adobe's media cache, sandboxed apps' container caches, Ableton Live's decoding cache (#139) | Delete permanently | Downloaded or rebuilt on next use |
| Build output | Xcode DerivedData project folders (products and dSYMs included), iOS DeviceSupport except the 2 newest versions per platform | Delete permanently | Rebuilt; next build is slower |
| Updater downloads | Sparkle and vendor updater caches | Delete permanently | Downloaded by the next update |
| Leaked app copies | Chrome `code_sign_clone` copies | Delete permanently, except the newest; the copy in use is listed unticked (#374) | Not needed again |
| Logs | User logs and crash reports | Delete permanently | Written again as apps run |
| Project build folders | `node_modules`, `.build`, `target`, `build`, `.venv`, `__pycache__`, `.next`, `dist` and project-relative `DerivedData` in folders you picked (#157) | Move to Trash | Rebuilt by the project's next install or build; or restore from Trash |
| AI tool transcripts | Claude Code and Codex transcripts and logs not opened in 90 days (#140) | Move to Trash | Restore from Trash in Finder |
| Downloads and installers | Every file in Downloads, at any size or age (#342, RESET Decision 83); iPhone, iPad and iPod update files (`.ipsw`) in `~/Library/iTunes/*Software Updates` (#135) | Move to Trash | Restore from Trash in Finder |
| Models | Hugging Face models; LM Studio models (each model folder; refused while LM Studio runs) | Move to Trash | Restore from Trash, or download again |
| Ollama models | Each model, removed with `ollama rm <model>` | Run a tool | Download again (`ollama pull`) |
| VM and disk images | e.g. an unpacked image next to its compressed source | Move to Trash | Restore from Trash, or the app unpacks or downloads again |
| Docker | Stopped containers, unused images, build cache: each its own choice, pruned in that order. Volumes never | Run a tool | Pulled or built again |

Other actions:

- **Run a tool**, with a time limit: `brew cleanup -s` (plus the Homebrew cache folder), `xcrun simctl delete unavailable`, `ollama rm <model>`, `pnpm store prune`, `uv cache prune` (in the folder `uv cache dir` names; Decision 44), `docker container prune -f`, `docker image prune -a -f`, `docker builder prune -a -f`, in that order: `image prune -a` keeps every image a container uses, stopped ones included, so stopped containers go first (Decision 85). uv's cache is changed only through uv, as its docs require: without uv its rule doesn't appear at all (it isn't shown as unavailable), and when `uv cache dir` fails, times out or prints no folder path, the plan says uv didn't say where its cache is. Either way its folder is never deleted instead. `uv cache clean` is never run. Every other cache is cleaned by deleting its folder, not with the tool's own purge command. The tool's output and the measured freed space appear in the results. A tool that isn't installed means its rule doesn't appear; CacheDrop never installs anything.
- **Where a developer cache is** (#170): npm (`npm config get cache`, its `_cacache` folder), pip (`python3 -m pip cache dir`), pnpm (`pnpm store path`), Homebrew (`brew --cache`) and uv (`uv cache dir`) are asked where their cache is, so a custom folder is found. Only each tool's known install locations are run, never one found on a PATH, with a time limit and without a shell, so no shell startup file runs. A folder the tool names that isn't its usual one is offered instead; one inside the usual folder (pnpm's versioned `~/Library/pnpm/store/v10`) counts as the usual folder, so the whole store is offered. Each such item's detail line says where its folder came from: "Named by `npm config get cache`" when the tool named it (custom or usual), or "Usual folder" when it didn't; the rule's description moves to its tooltip. The plan itself gets no note for a folder the tool named. When npm, pip, pnpm or Homebrew isn't installed there or doesn't answer with a folder path, the usual folder is offered and the plan says so; uv's is then never offered (above). A named folder gets the same scope checks as any other: one outside the home folder, missing, the home folder itself or one of its standard folders, or one that holds another rule's location, is never offered, and the plan says why. A named folder CacheDrop deletes (npm's, pip's and Homebrew's; #205) must also look like that tool's cache: it is never anywhere inside Applications, Desktop, Documents, Downloads, Movies, Music, Pictures or Public, and pip's must hold `http-v2`, `http` or `wheels`, Homebrew's `downloads` or `api`, as their docs and source describe (npm's is already its `_cacache` folder). Otherwise it is never offered, and the plan says why. pnpm's and uv's folders are only pruned by their own tool, so this doesn't apply to them. CacheDrop never runs npm or pip from a version manager (nvm, fnm, Volta, pyenv, asdf, mise; #201). When npm or pip isn't in a known location, its own config file is read as text instead, without running anything: `cache=` in `~/.npmrc`, and `cache-dir` in the `[global]` section of pip.conf (`~/Library/Application Support/pip/pip.conf` when that folder exists, else `~/.config/pip/pip.conf`, as pip reads them). A configured folder gets the same scope and cache-look checks as a named one, so `cache=~/Documents` is refused; its detail line says "Set in ~/.npmrc". A value CacheDrop can't follow (`${VAR}`, a relative path) offers nothing. Without a setting, the usual folder is offered and the plan says it's where the tool keeps its cache unless it was set otherwise. The check just before acting runs these scope and cache-look checks again on any folder a tool named or its config set. What an interrupted clean of such a folder left half-deleted (#202) is looked for next to it too, even when the folder itself is gone, as long as the folder isn't inside one of those user folders or holds more than its cache; each leftover gets the same scope checks, at the scan and before acting, but isn't asked for the cache-look entries a half-deleted cache may have lost.
  - A cancel or the time limit stops the tool and everything it started in its process group, and the results say it may have cleaned part of it. Docker's prunes, `simctl` and `ollama rm` hand the work to a daemon (Docker, CoreSimulator, the Ollama server) that CacheDrop can't stop, so for them only the wait stops: the results say the work may still be finishing (#185, #189). A minute after the run, each such item is measured again the way the scan measures it, and its record gains what went: gone, how much went and is left, or couldn't be measured, never "gone" when the daemon didn't answer. The recorded outcome and the measured freed space stay as they were (#190, Decision 45). A minute after Docker prunes that completed, the disk's free space is read once more; Results say the check is coming, then show how much more was free under the measured freed space, without counting it as freed (Decision 91).
- **Evict local iCloud copy** (#111): removes only the local download (`evictUbiquitousItem`); the original stays in iCloud and downloads again when opened. Items are the files and folders at the top of iCloud Drive; a folder evicts each qualifying file inside it, and a package counts as one file. Files set to Keep Downloaded (pinned), not yet uploaded, in conflict, or whose state can't be read are never offered, and the check just before acting refuses them. No public API reports Keep Downloaded, so CacheDrop reads the `com.apple.fileprovider.pinned#PX` attribute on the file and its folders; when it can't be read the file counts as pinned. Scanning reads metadata only, with placeholder downloads blocked for the scanning thread. This is never a delete.
- **Guidance only**: CacheDrop shows the size and tells the user where to manage it. It never changes these: iOS backups, Mail and Messages attachments, Photos, Time Machine local snapshots, Xcode release archives, purchased content such as audio plug-ins and Rack Extensions ("reinstall through the vendor", owner's call), AI agent workspaces (#140), and audio libraries (#139): the Logic Pro and GarageBand sound library, Ableton Packs and Splice samples. Kontakt and other Native Instruments libraries aren't listed: their default location, `/Users/Shared`, holds other apps' files too. (#114) They are catalog rules with the guidance action: sized from metadata only (never file contents), never candidates, and refused by the check if one ever reaches the executor. A location macOS won't let CacheDrop read shows as not accessible, never 0. Local snapshots show their count from `tmutil listlocalsnapshots /` with size unknown, since macOS reports no size per snapshot. Each has an "Open …" button: the owning app (Finder for device backups, Mail, Messages, Photos, Xcode), Storage settings for snapshots, or the plug-in folder in Finder. Audio plug-ins are also listed by product (#174, Decision 42): AU, VST, VST3 and CLAP in `/Library/Audio/Plug-Ins` and `~/Library/Audio/Plug-Ins`, AAX in `/Library/Application Support/Avid/Audio/Plug-Ins`, and AUv3 extensions in apps in `/Applications` and `~/Applications`. Files are grouped by installer receipt (`/var/db/receipts`, read with `lsbom`), then by bundle ID vendor and name; files nothing ties stand alone. Relative install prefixes in this startup-volume scan resolve under `/`, so `Library` means `/Library`; missing recorded paths are skipped without searching a home folder or relocated location (#329, Decision 113). A malformed/unreadable receipt or a receipt database that cannot be listed withholds all plug-in support and installed vendor content, while removable format bundles remain offered. Support paths must be reached without a symlink from the system root at the scan and before acting; existing ownership, sharing, license and selection checks still apply. Each product shows maker, version, formats and size on one short line, with architectures, place and its files in the tooltip; clicking it reveals it in Finder, and VoiceOver says "Reveal <product> in Finder" (#207). The Audio plug-ins total counts only those format folders (AU `Components`, `VST`, `VST3`, `CLAP` and Avid's AAX folder), not `HAL` or `MIDI Drivers`, and its "Open in Finder" opens the first of them that exists, in that order (`/Library/Audio/Plug-Ins/Components` first). Only Info.plist, `moduleinfo.json` and the executable's Mach-O header are read; plug-in code is never loaded. Apple's own plug-ins are never removable, and nothing is called unused or a duplicate. Photos libraries (#180) are every `.photoslibrary` package in the home folder (not `~/Library`, hidden folders or apps, at most 6 folders deep) and on each local volume connected under `/Volumes`, to the same depth, found by name in one search that never enters a package, within the guidance time budget; network volumes are never searched, and each volume is searched on its own thread, so one whose reads hang (a dropped share) is abandoned at the deadline and named "not searched" in the summary (#244); each shows its volume and size, and is revealed in Finder. The steps are Photos' own: Optimize Mac Storage, or moving the whole library (Apple Support 108345); deleting photos in an iCloud library deletes them on every device. Final Cut Pro libraries (#178) are every `.fcpbundle` package, found by the same search and listed the same way; Open Final Cut Pro, then File → Delete Generated Library Files (Apple Support 119610). Render files are made again as you work; optimized and proxy media must be created again, which needs the original media online. Lightroom Classic previews (#179) are every `<Catalog> Previews.lrdata` and `<Catalog> Smart Previews.lrdata` package, found by the same search, as two rows counted by catalog: normal previews are built again when photos are viewed (Library → Previews → Discard 1:1 Previews, or Catalog Settings → File Handling); Smart Previews let photos be edited while their originals are offline (Library → Previews → Discard Smart Previews). Catalogs (`.lrcat`), Lightroom's other `.lrdata` packages and backups are never listed or offered. Without Full Disk Access, both Lightroom rows show only when Launch Services knows `com.adobe.LightroomClassicCC7` (#247). Opening an app only reports that it opened, never cleanup done, and library bytes never count as freed. The search needs Full Disk Access, since it reads Desktop, Documents and removable volumes. Without it, the Final Cut Pro row ("Needs access") shows only when Launch Services knows `com.apple.FinalCut`; with access, it shows whenever a library is found, installed or not (#245). Audio libraries open their own manager (Logic Pro's Sound Library Manager, Live's browser, Splice); when that app doesn't open, usually because it isn't installed, the folder is revealed in Finder instead.

Notes per category:

- **Browsers** (Chrome, Safari, Firefox): cache folders only, per profile, only while that browser is closed. Sizes show per browser and per profile. Review says caches are permanently removed, will refill, and pages may load slower at first.
- **Arc and Edge** aren't covered yet (#116): their makers don't document where the macOS caches live, so neither has a rule.
- **Safari** (#117): only WebKit's HTTP cache, `~/Library/Caches/com.apple.Safari/WebKit/NetworkCache`. The rest of that folder (CacheStorage, HSTS), history, bookmarks, cookies and website data are protected. Safari's container and per-profile caches aren't offered until their layout is confirmed. macOS protects Safari's data, so without Full Disk Access the row says not accessible, with the explanation, and nothing there is read.
- **Chrome code-sign clones** live in the user's own folder under `/private/var/folders`. The newest copy is always kept. The copy the running browser has open stays on the plan, unticked, with "In use by Google Chrome · Quit Google Chrome to clean it" (#374).
- **Old temporary files and app caches** (#132), under App caches: each file or folder at the top of the user's own `T` folder, and in its `C` folder only a folder named after an installed app's bundle identifier, with that app closed (macOS's own daemon caches there, such as `assessmentagent` or `clang`, are never offered). Either is offered only when the user owns all of it, nothing inside was modified or changed in 3 days, it isn't empty, and it isn't macOS's (`com.apple.*`) or another rule's. One a process of the user's has a file in open or mapped stays on the plan, unticked, with its reason (#374), and is deleted only if nothing has it open at Clean up. When open files can't be read, nothing is offered. Open and mapped files are read through the documented libproc calls, once per scan and once per review. A cleanup run reads them again before each item that needs this check once the last reading is more than 5 seconds old, so an item that comes after a long step is checked against what is open then (#142). The check just before acting repeats the in-use check and refuses an item anything inside changed in since the scan. `X` is never touched except by the Chrome rule.
- **Xcode**: whole DerivedData project folders, only while Xcode and its build processes aren't running. Archives are never candidates.
- **Docker**: sizes are estimates of what each prune removes, from one `docker system df` per scan (plus its `-v` list when a container stays after `container prune`), with a short time limit: never space a prune can't free: the build cache less layers an image still in use shares, every image but those the containers left after `container prune` use, and the stopped containers (Decision 90). When the `-v` list can't be read, the images and build cache sizes are unknown. Docker must be running, the inverse of other owners; when its daemon doesn't answer, a notice says so and no size is shown, never 0. Volumes hold databases and app data, so they are never pruned.
- **Ollama**: shared blobs make per-file Trash unsafe, so models are removed with `ollama rm` (an exception to Decision 3).
- **Per-app caches**: only while the owning app isn't running. A folder that holds an app's offline or downloaded content is never offered whole and is refused by the check (#171): Spotify's while an `offline.bnk` file is anywhere inside, whatever folder name Settings > Storage was given (#203), or a `Storage` or `storage` folder sits right in it (#171). Every other item in the app's folder is offered; the item holding the downloads stays out (#243). A web-view profile inside an app's cache folder (a folder holding `Cookies`, `Login Data` or `Local Storage`, within four levels) is never offered whole, so cleaning never signs the user out of the app's web views (#203), and Chromium's `Local State` (its profile list and settings) is never offered (#243): only its `Cache`, `Code Cache` and `GPUCache` are offered, with every other item in the app's folder (Spotify's `Data` streaming cache, say), grouped under the app (#241). Inside such a folder, an item that holds offline content or sits in a folder holding it stays out. The check re-applies this: it refuses the whole folder if sign-in data appears, an item that became a profile or gained offline content, and a part whose folder no longer holds a profile. Each exception cites vendor documentation or an observed layout in `AppCaches.offlineContent`; an app not audited keeps this rule as is.
- **Caches outside `~/Library/Caches`** (#133), each only while its app isn't running:
  - VS Code, VSCodium, Cursor and Windsurf: `Cache`, `CachedData`, `CachedExtensionVSIXs`, `Code Cache` and `GPUCache` in `~/Library/Application Support/<Code|VSCodium|Cursor|Windsurf>`; never `User`, `extensions` or backups. Refused while that editor runs (#140). Copilot keeps its data in VS Code's folders, so it has no rule of its own.
  - JetBrains: `~/Library/Caches/JetBrains/<product><version>` of older versions only. Never offered: the folder of any installed version (read from the IDE's app bundle, `product-info.json` or else its Info.plist), every folder of an IDE installed in a version CacheDrop can't read, the newest folder of each IDE, and products CacheDrop doesn't know (#145). Refused while any version of that IDE runs.
  - Adobe: `Media Cache Files` and `Media Cache` in `~/Library/Application Support/Adobe/Common`, refused while an Adobe video app runs.
  - Ableton Live: `~/Library/Caches/Ableton/Cache`, its decoding cache, refused while Live runs. Logic Pro, GarageBand, Pro Tools and Native Instruments have no rebuildable cache CacheDrop offers: none is documented outside projects, and Kontakt's database is an index, not a decoding, waveform or analysis cache. Freeze files and bounces inside projects are left to the explorer (#113).
  - Sandboxed apps: only `~/Library/Containers/<bundle id>/Data/Library/Caches`, never other container data or group containers; the app must be installed and closed. Reading containers can make macOS ask for access, so without Full Disk Access the rule shows as not accessible and nothing there is read.
- **AI coding tools** (#140):
  - Claude Code: `*.jsonl` transcripts under `~/.claude/projects`, never its `memory` folders; Codex: `*.jsonl` sessions under `~/.codex/sessions` and `~/.codex/archived_sessions`, and `~/.codex/log`. Only files not opened, changed or added in 90 days, to Trash. Settings, credentials, project memory and prompt history are never offered.
  - Agent workspaces are guidance only, never offered even when clean: git checkouts and build scratch in `~/.codex/worktrees`, `~/Library/Caches/Codex` and Claude Code's `/private/tmp/claude-<uid>`. The row shows their size and git status ("4 workspaces · 1 has uncommitted changes · 2 have unpushed commits"), read with `git status --porcelain` and `git rev-list --count @{u}..HEAD` (without an upstream, commits on no remote), each with a 5-second limit. Git runs read-only as far as it can be made to (#147): no optional locks, so it never refreshes the index; fsmonitor and hooks off; no lazy fetch in a partial clone; submodules never entered (only a submodule moved to another commit counts, not changes inside one); untracked files still count as uncommitted. Remaining caveat: git still reads the repository's own `.git/config`, so a clean or process filter driver it names for a file in `.gitattributes` can still run when `git status` compares that file's contents; that filter is a command the repository's author configured, and CacheDrop can't turn it off without knowing its name. "Open in Finder" shows the folder.
- **Build folders in your projects** (#157): inside folders you picked, each kind is recognised only beside its project's marker: `package.json` for `node_modules`, `.next` and `dist`; `Package.swift` for `.build`; `Cargo.toml` or `pom.xml` for `target`; `build.gradle(.kts)` for `build`; `pyproject.toml`, `requirements.txt` or `setup.py` for `.venv` and `__pycache__`; an `.xcodeproj` for a `DerivedData` folder beside it. The walk never enters a found build folder, hidden folders, git's data or the home Library, and stays bounded (8 levels, 20,000 folders, 500 projects). The plan shows one row per project with its size and last-modified date (the newest file outside its build folders and `.git`); you choose each project, nothing is preselected and Smart clean never takes them. A project is left out at the scan and refused just before acting while it is too big to date (100,000 files), or git tracks files inside the build folder itself. One that any of your processes has a file in open, that changed in the last 7 days, or where git reports uncommitted changes to tracked files (`git status --porcelain --untracked-files=no`, read-only as for agent workspaces) stays on the plan, unticked, with that reason (#374): ticking it overrides the last two, while one still open is refused just before acting. A build folder holding a git working tree is never offered, as in section 2, except a SwiftPM `.build` whose only git working trees are its own dependency clones in `checkouts/` (#160); the project's own uncommitted changes still keep it.
- **Models and VM images** show their size and last-used date so the user can judge.
- **A cleanup rule appears only when its tool or folder exists** on this Mac.
- **Overview** shows one row per category that found something. Its storage bar is the whole disk, used against available, as in the prototype's full mode; it never splits the bar by category. Under the categories, a Scanned locations group lists each folder the user chose, with its size, an Explore link and its own reason when the scan couldn't read everything (RESET Decisions 81 and 82).

## 4. Checks just before acting

When the user confirms, CacheDrop freezes the plan. Then, for each item in turn, right before acting, it checks that:

1. the item still exists;
2. it is unchanged since the scan: the same file identity. A file must also have the same size and modification time. A folder is checked for identity only, not modification time, because caches change constantly;
3. its owning app is not running, or for a command-line tool's cache (npm, pip, Cargo and the like), no process of that tool is running; for a file from a deleted app, no process of its maker is running, for any user, background helpers included, and a process list that can't be read refuses it (#240);
4. it is not excluded and doesn't match a protected rule;
5. CacheDrop can act on it as the current user, without admin rights;
6. for leaked app copies and old temporary items, no process has it open or mapped, as read no more than 5 seconds earlier (#142).

An item that fails any check is skipped, and the results say which check failed. The rest of the plan continues. Skipped items can be reviewed again after a fresh scan; CacheDrop never silently repeats a completed action or widens a plan after a rescan.

**Cancel** stops new items from starting. A cleanup tool that is running is stopped at once and recorded as partly removed, its folder left in place; one not yet launched never starts (#166). Docker's prunes, `simctl` and `ollama rm` hand their work to a daemon, so for them only the wait stops and the work may still be finishing; a minute later the item is measured again and the journal records what went (section 3, #185, #189, #190). Any other item in progress finishes or reports its failure. Every item's outcome (done, skipped, failed, not started) goes into the cleanup journal. Quitting during a run asks first, "A cleanup is running. Stop it and quit?", with Cancel as the default; confirming cancels as above and quits once the current item ends (#130). If CacheDrop quits in the middle of a run anyway, it recovers the journal on next launch and reports what happened.

**Interrupted cleanup** (#309). A run whose items have no recorded outcome (not started, started, or unknown) is interrupted until it is reviewed. Launch stays on Overview, which shows "Interrupted cleanup needs review"; Recovery opens from there, from History or from a page's run. Opening Recovery checks each such item against disk, read-only: at its original location with the identity it had at approval is "Not removed"; in the Trash (its recorded Trash location, its own name there, or any Trash item with its identity) is "Moved to Trash"; gone from both is "Removed"; never started is "Not started". Anything CacheDrop can't tell stays "Unknown": something else at its path, a delete's renamed-aside copy still there, a tool or iCloud item still in place, or a location or Trash it can't read. **Mark as reviewed** checks again, and records the findings only if they are unchanged; for an unknown item it is the user's confirmation. Recording appends one reviewed record per item to the journal; the original records are never rewritten. A reviewed run no longer counts as interrupted: the banner goes, Reset works, and History shows the run with its findings, with Put back for an item found in the Trash.

## 5. Dry-run switch

- The review sheet is the preview: it lists exactly what will happen, and **Clean up** runs it for real (Decision 27). The plan has no preview mode.
- The dry run is a switch in the Settings window, **Dry run (nothing changes)**, off by default and meant for testing. While it's on, the review sheet says so in one line.
- With dry run on, the whole flow runs as normal: scan, plan, review, confirm, per-item checks, results.
- Instead of acting, CacheDrop logs each action it would take (item, action, size, check outcome) and changes nothing on disk. Tool actions are not run; the command is logged.
- Results make clear it was a dry run. No freed space is reported, because none was freed.

## 6. Estimated vs measured freed space

- **Size wording** (Decision 96): every page and report shares decimal formatting. Exact values are unqualified; estimates say "About", upper bounds "Up to", partial positive measurements "At least", and unreadable sizes "Unknown", never zero. Profile rows retain the same qualifiers as their category's size policy.
- **Estimated** space is what the scan sizes before cleanup, from allocated size where available. Overview's "Recommended for review: up to X GB" is the sum of current catalog candidates whose action frees space (delete or run a tool), labeled as an estimate. Items bound for the Trash are shown separately, because their space stays used until the Trash is emptied.
- **Moved to Trash** is reported on its own. That space is still used until the user empties the Trash, and is never counted as freed. Results and Overview offer **Empty from Trash…** for CacheDrop's own items still there (RESET Decision 68); that emptying is measured around each item, as a cleanup is.
- **Measured freed space** is the change in the volume's available space, read right before and right after each item. Results report the measured total, separately from the estimate. After Docker prunes, what more was free a minute later shows under it, never in it (Decision 91).
- **Why both:** on APFS, clones share disk blocks. Deleting a clone frees only the blocks no other file uses. Chrome's code-sign copies showed 52 GB but freed about 2 GB. For categories made of clones, the estimate is labeled as an upper bound.
- **Why measure per item:** on a nearly full disk, macOS releases purgeable space on its own, so a single before/after reading for the whole run overstates what CacheDrop freed.
- Measured space is an observation. Downloads, snapshots and other activity can affect it, and the results say so.
- **Pass bar for M1:** on the user's Mac, the freed space CacheDrop reports is within 10% or 1 GB (whichever is larger) of the `df` change measured around the whole run.

## 7. Access: user-owned scope

- CacheDrop works only in what the current user owns: the home folder, `~/Library`, and the user's own entry under `/private/var/folders` (its `T`, `C` and `X` folders). It never asks for admin rights (Decision 4). The one exception is uninstalling (RESET Decisions 41 and 50): an app or plug-in the user chose, and its files, go to the Trash when macOS lets the user move them there without a password, whoever owns them, checked at the scan and again before acting.
- It sizes only the catalog's known locations, plus folders the user picks. It never walks the whole disk.
- **Full Disk Access is optional**, a way to "see more" (for example Safari's cache, which macOS may protect). Without it, CacheDrop works and lists what it couldn't read as not accessible. CacheDrop explains that Full Disk Access is broad read/write authority, not a read-only permission, and that CacheDrop's own scans stay read-only.
- CacheDrop asks for access when a feature needs it, not as a launch checklist. No Accessibility, Screen Recording, notifications or login item is needed to scan or clean. Notification permission is asked for only when you turn low-space alerts on (#131).

## 9. Out of scope

- Duplicate finder, treemap, automatic or scheduled cleanup. (Uninstalling was listed here; RESET Decisions 41, 50 and 51 brought it into scope: apps, plug-ins and files from deleted apps go to the Trash from the Applications page.)
- Emptying the Trash. (Deleting from it only what CacheDrop moved there, when asked, is in scope: RESET Decision 68.)
- Admin helpers, root daemons, system extensions, anything that needs an admin password.
- Other users' data and system files; blanket cleanup of System Data, Application Support, containers, snapshots or swap.
- Changing Photos, Mail or Messages libraries or databases.
- Speed boosts, RAM cleaning, antivirus and similar.
- Cloud accounts, cloud-wide deletion, remotely updated cleanup rules.

## Manual updates

Check for Updates… in Settings and the app menu uses the same Sparkle updater and its standard dialogs. Checks happen only on request; scheduled checks, automatic downloads/installations, the automatic-check permission prompt and system profiling stay off (Decision 102).

An approved installation waits for cleanup and maintenance to finish naturally. While pending, new cleanup, maintenance, scans and deferred scans cannot start. Scan discovery stops and final saved writes finish; optional sleeping measurements are skipped and running measurements finish saving. Waiting for cleanup to finish or Finishing current work offers Cancel update until installation handoff. Cancel leaves active work running and restores normal availability without a stale installation callback. Installation never uses Stop and Quit; relaunch preserves saved state and restores no cleanup selections or operations (Decision 103).
